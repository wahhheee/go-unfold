# 架构与演进边界

## 当前选择

React + TypeScript 管理应用状态和组件，Vite 构建静态站点，React Router 提供客户端路由，MDX 将课程正文与交互组件组合。Shiki 在构建期生成代码高亮；正文、各实验组件与 JSON 高亮编辑器按需加载，避免课程增长时首屏携带全部模型和高亮引擎。

应用本身不需要服务端。教学偏向 Go 并不意味着必须用 Go 搭建一个没有服务端需求的服务。以后需要账号同步或真实代码执行时，再添加独立服务，避免现在引入无用的数据库和部署依赖。

## 内容边界

`content/` 管理编排与题目；`lib/` 只管理可验证模型；`components/` 负责展示与交互；`pages/` 聚合学习入口；`state/` 处理浏览器记录及输入校验。模拟模型不依赖 React，便于单独验证或复用于不同视图。

已发布内容以 `lessons.ts` 注册表为准，前三章逐节交付记录见 `GO_CHAPTER.md`、`CONCURRENCY_CHAPTER.md` 与 `NETWORK_CHAPTER.md`。注册表与 `curriculum.ts` 中的课程规划独立：前者生成真实入口，后者描述覆盖九个模块的路线，不意味着这些模块已经写完。模块完成审计后设置 `contentComplete`，统一更新地图状态与搜索中的规划项。

## 章节注册与学习记录

1. `LessonDefinition` 统一定义章节元信息与 MDX 加载函数；`LessonContext` 为正文组件提供当前章节资料。
2. `/learn/:lessonId` 是通用渲染器，读取注册表中的正文和目录；未知 ID 使用 404 页面。
3. 学习记录使用 `go-deeper:learning:v2`，内容为 `{ version: 2, lessons: { [lessonId]: LearningState } }`。初始 `v1` 记录可以自动迁移到 `preface`，不会先删除原记录。
4. 题目有 `lessonId` 和全局唯一的题目 ID，随堂练习读写所属章节，练习回顾聚合所有章节，章节目录只计算本节题目。
5. 侧栏、搜索、知识地图和进度统一读取注册表；笔记页面按章节选择，并可一次导出所有已发布章节的笔记。

未来再次修改存储结构时，添加显式版本与迁移测试，保持已有笔记、收藏和答题记录。章节 ID 与题目 ID 是持久数据的键，不应随标题修改。

品牌已更名为 Go 探原 / Go Unfold，主题与学习记录仍保留历史 `go-deeper:*` 键，避免同一来源下已有数据因改名丢失。不同域名、协议或端口的浏览器记录不会自动跨来源迁移。

## 持久化与隐私

首版仅使用 `localStorage`，不采集学习行为、不向服务器传送笔记。恢复数据时验证题目下标和笔记类型；存储不可用时显示提醒，当前会话仍可继续。导出笔记使用浏览器 Blob，不依赖外部服务。

## 测试策略

Vitest 覆盖模拟状态机的失效边界、全部参数区间的事件顺序和不可信存储恢复。Playwright 覆盖浏览器流程、手机导航、主题持久化、JSON 校验、答案持久化与笔记下载，axe 检查基本无障碍规则。截图人工检查仍然必要；axe 通过不能证明交互在所有辅助技术上都没有问题。

内容注册测试防止章节、锚点和题目 ID 冲突，检查题目归属与答案结构。通用浏览器测试从注册表生成逐节正文、练习、追问、主题与持久化检查；三章的实验流程另有显式检查，整章测试覆盖入口、搜索、首尾翻页和笔记隔离。

`examples/go/` 是独立的 Go 模块，通过真实工具链验证语言行为，固定 x/sync 与 x/time 的版本。CI 执行普通测试、vet、race 和短时 fuzz；性能与并发诊断案例另有可复验命令和测量记录。有意 panic、数据竞争和永久阻塞在带超时的子进程中验证，避免污染主测试进程。浏览器模型与真实 Go 验证分别标明能力范围，不把模拟动画当作 Go 运行时。

第三章网络样本只访问回环地址或受控解析传输，使用临时端口、证书和文件；Linux 专用的 fd、mmap 与 epoll 验证通过文件名限定平台。浏览器模型声明省略的网络事件与内核细节，真实样本不修改系统参数、不依赖外网、不模拟任意代码执行。

## 部署

构建产物是静态文件。Vite 的 base 与 BrowserRouter 的 basename 一致；图片与 favicon 使用同一资源前缀。`scripts/prepare-static.mjs` 从课程注册表生成每节真实入口，另包含地图、练习、笔记和 404，因此 GitHub Pages 不需要服务器端 SPA 重写。应用统一处理静态目录的尾斜线。

静态发布检查使用无 SPA 回退的本地服务器，确认直接访问与刷新确实命中已生成文件。工作流仅在全部检查成功后从 main 部署，第三方许可文件随产物分发。正式内容的更正通过 Git 提交和变更记录追踪，详见 `DEPLOYMENT.md`。
