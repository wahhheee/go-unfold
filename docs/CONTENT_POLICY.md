# 内容核验与更新规范

## 证据优先级

语言规范、官方文档、对应版本源码与可复现实验优先。博客、面经与论坛只作为发现问题的线索，不直接作为正确性的依据。

讲清三种不同性质的陈述：规范要求、当前实现、工程建议。比如 Go 内存模型的保证与某版本运行时的实现不能混写，某次压测得出的经验也不能包装成定律。

## 每篇的核验信息

- 列出实际引用的一手资料，而不是给出泛泛的官网首页。
- 标注核验日期，说明适用产品与必要版本。
- 资料使用 `current` 或 `latest` URL 时，核验日期不能自动随页面打开更新。
- 发布前重新访问引用资料；链接仍然可用不等于结论没有变化。
- 因版本更新修改结论时，在 `CHANGELOG.md` 记录变化与原因。

当前序章于 2026-09-19 核验。重点包括 `SETNX` 的弃用状态、`SET NX PX`、Lua 原子执行、Redis 8.4 的 `DELEX IFEQ`、异步复制失锁、`WAIT` 的一致性边界，以及 PostgreSQL 与 InnoDB 的默认隔离级别。

第一章同日以 Go 1.27.1 / linux / amd64 核验，语言结论对照规范，实现结论对照版本源码和官方发布说明，并保留 `examples/go/` 中的可执行证据。涉及 Go 1.22 循环变量、1.24 Swiss Table、1.25 容器默认策略与 synctest、1.26 Green Tea 和 AsType、1.27 泛型方法与泄漏画像的内容，必须保留各自的版本前提。升级工具链后，先复核这些边界，不能只替换核验日期。

第二章同日沿用该工具链，固定 x/sync v0.23.0、x/time v0.16.0。升级时重点复核 Go 1.27 移除 asynctimerchan 旧开关、WaitGroup.Go 的 panic 契约、Cond 的条件重检、Context 回调与退出、errgroup 的 Wait 取消、singleflight 的在途共享、加权信号量的等待行为、令牌预约的退还限制，以及 goroutineleak 的可达性盲区。库实现中的队列、公平性与阈值不能包装成语言规范或等待时间承诺。

## 不制造“毒八股”

避免“永远”“绝对安全”“一定不会”等缺失前提的结论。命令名、技术名词和工具名称不能代替推理。

例如，随机 token 的比较删除防止误删别人的锁；资源端原子校验单调 fencing token 才能拒绝已观察到更新令牌之后的旧写入。续租、随机所有权 token、fencing 和幂等解决的问题不同，应分别解释。

涉及 PostgreSQL 时说明隔离级别、普通读取或锁定读取、事务范围；提到 MySQL 时标明 InnoDB 等具体引擎，不能套用一个产品的默认值。

## 实验与代码

所有模拟必须说明省略的真实系统因素。示例代码要说明前置依赖、执行环境与失败处理；片段不得声称是完整生产实现。

答案还应说清反面：本次实验没有发生故障，能排除什么，不能排除什么。对网络超时、结果未知、部分成功和重试副作用不能简单归为“失败后重试”。

## 更新节奏

语言、数据库或基础组件有相关版本发布时，人工复核受影响章节。未实际核对前保留原日期并记录待核验项。项目不假装自动获取了“最新知识”，也不对未发布内容展示已核验标识。
