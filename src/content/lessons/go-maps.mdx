## map 的赋值共享条目，缺失键读取返回零值。

一个请求统计器把 `counts` 传进函数，函数写入新计数，调用者能看到变化。这仍是按值传参：复制的 map 值连接到同一个底层数据结构。在函数中重新 `make` 并赋给形参，则不会替换调用者保存的 map 值。

```go
m := map[string]int{"ok": 0}
n := m
n["ok"]++
value, exists := m["missing"]
fmt.Println(m["ok"], value, exists) // 1 0 false
```

只看 `m[key] == 0` 无法区分“没有这个键”和“有这个键但值为 0”。权限、库存、计费这些场景必须认真对待 comma-ok 的第二个结果。`make(map[K]V, n)` 中的 n 是初始容量提示，不是限制；map 没有可用来获取容量的 `cap` 操作。

`var m map[string]int` 是 nil map：读取、len、range、delete、clear 可以使用，但写入条目会 panic。map 只能与 nil 直接比较，不能用 `m1 == m2` 比内容。

### 键必须可比较，还要考虑比较的业务含义

切片、map、函数不能直接作为键；可比较的数组和结构体可以。`map[any]int` 虽然能编译，塞入动态类型为切片的键仍会 panic。浮点 NaN 也值得单独注意：它可比较，却不等于自身。

```go
x := math.NaN()
m := map[float64]int{x: 1}
_, ok := m[x]
delete(m, x)
fmt.Println(ok, len(m)) // false 1
clear(m)
fmt.Println(len(m))     // 0
```

哈希查找最终仍要比较键，NaN 的非自反性让“用原来的变量查回去”也失败。需要精确身份的业务键，应选择符合业务等价关系的表示，不能把浮点数当作万用标识符。

### map 索引不能当作稳定的元素地址

`&m[key]` 不合法。若 `m` 的值类型为结构体，也不能直接 `m[key].Count++`；通常取出值、修改、整体写回。`map[K]*Entry` 可以修改指针所指对象，但对象共享、nil 检查和并发同步问题随之出现。索引不可寻址是语言规则，不必把它简化成“永远只是因为扩容搬家”。

## 遍历顺序没有保证，也不是均匀抽样。

不要依赖插入顺序、上一次遍历顺序或“一直测起来都这样”。取第一个键当作随机选择，还需要均匀性保证，而 map range 没提供这种抽样契约。需要稳定展示或签名输入时，提取键后按明确规则排序：

```go
keys := slices.Sorted(maps.Keys(counts)) // Go 1.23 起的迭代器 API
for _, key := range keys {
    fmt.Println(key, counts[key])
}
```

这里假设没有并发写，或者外层已持有所需锁。先复制键、释放锁、再从变化的 map 取值，不自动构成某个时刻的一致快照。需要快照时，要在同一同步边界内复制需要的键和值，并说明值里是否还含共享引用。

单 goroutine 在 range 中修改 map 有明确规则：尚未遍历到的条目若被删除，之后不会产生；新创建的条目可能产生，也可能被跳过。这是允许的迭代语义，与多个 goroutine 未同步读写同一个 map 是两个问题。

## Go 1.24 起，主线 map 使用 Swiss Table 设计。

旧面经常画 bucket、overflow bucket 和旧实现的搬迁过程。阅读老代码时它们仍有价值，但回答当前运行时不能忽略版本变化。以下观察以 Go 1.27.1 实现为基线，不属于语言对所有实现的承诺。

当前实现把键值槽组织成组，每组八个槽，配有控制字节。控制信息记录空、删除或短哈希 H2；查找时先批量比较短哈希，减少需要逐个比较完整键的数量。**H2 匹配只是候选，不是命中。** 碰撞仍需完整键比较与继续探测。

<MapProbeLab />

为什么删除槽有时保留墓碑？如果把探测链中间的位置直接标成“从未使用的空位”，查找可能太早停止，漏掉后面的键。墓碑表示这个位置曾参与过探测关系，不能直接当作结束条件。实际实现并非每次删除都必须留墓碑，要看所在组的情况。

当表需要增长时，探测布局随之改变。当前大 map 用目录连接多张表，让表按需增长和分裂，限制一次表增长的范围。这不等于每次插入都没有分配、不需要搬动条目，也不承诺每次操作具有严格恒定耗时。

## 普通 map 的并发写，需要明确同步。

不同 goroutine 写不同 key，也可能共同修改 map 内部结构，不能因此免锁。没有并发写并且安全发布后，并发读取可以成立；读取、遍历、len 与写入混用则都要检查同步边界。

```go
type Counter struct {
    mu sync.Mutex
    m  map[string]int
}

func (c *Counter) Add(key string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    if c.m == nil { c.m = make(map[string]int) }
    c.m[key]++ // 读、加一、写回，全部在锁内
}
```

读取同一个 m 的方法也必须遵守这把锁的约定，不能只给写方法加锁。Counter 使用后不得按值复制，因为包含 Mutex。方法签名和对象生命周期，需要共同维护这个约定。

`sync.Map` 提供并发安全的单次操作，以及 `LoadOrStore`、`CompareAndSwap` 等具体原子操作。但 `Load → 计算 → Store` 不是自动原子的“事务”，两个调用者仍可能读到同一旧值并互相覆盖。跨键库存不为负、总额守恒、限额检查等业务条件，也不会因为换了容器而自动成立。

<Quiz id="go-map-atomic" />

如果遇到运行时检测到并发 map 访问导致的 fatal，不要尝试用 recover 维持运行。这不同于可恢复的普通 panic；而没有 fatal 也不证明没有数据竞态。后面的测试一节会说明 race detector 的覆盖边界。
