<div className="section-kicker">03 / 小切口，完整理解</div>

## 不止一句 SETNX。

先限定问题：多个服务实例想更新同一份资源，希望同一时刻只由一个实例处理。进程内的 `sync.Mutex` 不能协调不同实例，于是我们尝试借助 Redis。

这里的锁更准确地说是**租约**：Redis 只在一段时间内保留你的所有权记录。租约结束，不代表你的业务代码已经结束。

### 第一步：获取锁和设置过期时间，必须原子完成

```redis
SET lock:order:42 unique-request-token NX PX 5000
```

- `NX`：键不存在时才写入。
- `PX 5000`：有效期为 5000 毫秒。
- `unique-request-token`：每次获取生成的新随机标识，用于证明本次所有权；不是固定的机器 ID。

这个命令把“检查不存在、写入、设置过期”放在一个原子操作里。只有明确收到成功响应，才能按协议进入临界区；失败要按策略等待或放弃。**网络超时属于结果未知，不能直接视为获取成功。**

<Callout title="更新一下旧答案" kind="note">
  `SETNX` 自 Redis 2.6.12 起已被标记为弃用，推荐使用带 `NX` 的 `SET`。更关键的是：不要把 `SETNX` 和
  `EXPIRE` 拆成两条独立命令。二者之间进程一旦崩溃，就可能留下没有过期时间的锁。
</Callout>

<Quiz id="atomic-acquire" />

### 第二步：释放时，原子校验所有权

A 的租约过期后，B 可能已经获取同名的新租约。如果 A 完成工作后直接执行 `DEL`，就会把 B 的锁删掉。一个兼容较早版本 Redis 的写法，是使用 Lua 脚本：

```lua
-- 比较和删除必须在 Redis 服务端原子完成
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
end
return 0
```

这里 `KEYS[1]` 是锁键，`ARGV[1]` 是本次获取时使用的 token。Redis 原子执行这段脚本，其他客户端的命令不会插进“比较”和“删除”之间。脚本应保持短小，因为执行期间会阻塞其他命令。

<Callout title="Redis 8.4 及之后：还有原生命令" kind="note">
  Redis 8.4 引入了 `DELEX key IFEQ token`，可直接进行原子比较删除。上面的 Lua
  写法用于展示机制，并兼容早于 8.4 的版本。选用命令前，要检查实际部署版本；不应再把“解锁必须写
  Lua”当作永远成立的结论。
</Callout>

<Callout title="到这里，还没有证明业务安全" kind="warning">
  Lua 解决的是“别删别人的锁”。如果 A 暂停太久，恢复后继续扣库存，即使没有误删锁，它仍可能与 B
  的业务发生冲突。**租约所有权与资源写入权限，需要分别考虑。**
</Callout>

## 让问题发生，比记住问题更有用。

下面，A 的租约只有 **5 秒**，但它要到第 **9 秒**才写入。B 在第 6 秒尝试获取锁。先预测：如果解锁时检查了 token，A 的旧写入还会成功吗？

<LockLab />

对比四种情形：默认场景中，A 仍能写入；关闭解锁校验，A 还会误删 B 的锁；启用续租却保留长暂停，续租线程也无能为力；打开资源端 fencing 后，已经接收过较新 token 的资源才会拒绝旧写入。

如果关闭长暂停、启用续租，本次模拟中 A 就能保持租约。这里的“成功”只对当前时间安排成立，不能外推为网络分区或进程长暂停下的保证。

### 那工程里，到底怎么选？

如果锁用于合并重复的缓存重建，偶发重复计算也许可以接受。如果它保护库存、余额或唯一业务记录，就应该先考虑数据库事务、条件更新、唯一约束与幂等设计，让数据本身守住不变量。

```sql
-- PostgreSQL：由数据库原子地检查库存并扣减
UPDATE inventory
SET available = available - 1
WHERE sku_id = $1 AND available > 0
RETURNING available;
```

只有返回一行才代表扣减成功；零行可能是商品不存在，也可能是库存不足。这条语句能守住非负库存，但**不能自动解决同一订单重试导致的重复扣减**，还需要订单幂等键、唯一约束与合适的事务边界。

<details className="go-example">
<summary>放到 Go 服务里：把上下文和错误继续传递</summary>

```go
package inventory

import (
    "context"
    "database/sql"
)

// ReserveOne 返回剩余库存，零行结果会返回 sql.ErrNoRows。
func ReserveOne(ctx context.Context, db *sql.DB, skuID int64) (int64, error) {
    const query = `UPDATE inventory
        SET available = available - 1
        WHERE sku_id = $1 AND available > 0
        RETURNING available`

    var remaining int64
    err := db.QueryRowContext(ctx, query, skuID).Scan(&remaining)
    return remaining, err
}
```

调用方需要使用支持 PostgreSQL 的驱动创建 `*sql.DB`，且仅在 `err == nil` 时使用结果。`sql.ErrNoRows` 需要转成合适的业务结果；网络错误还可能意味着提交结果不明，不能因此盲目重试。传递 `context` 有助于取消等待，但也不等于已经发生的数据库副作用被撤销。

</details>

<Callout title="不要把 Redlock 当作结束讨论的咒语" kind="warning">
  多节点协议仍然有时间与故障模型的前提，不能因为“多数节点成功”就推导出所有场景下严格互斥。正确性要求高时，应明确评估具备所需一致性语义的协调服务，并把资源端校验纳入设计。完整协议与争议将在分布式系统章节展开。
</Callout>
